# 拾题成卷 GitHub 协作与开源发布方案

2026-11-04 · 计划阶段

拾题成卷 计划开源，开发需求和缺陷在 GitHub Issues 跟踪。产品行为以[产品需求文档](产品需求文档-V1.md)为准，阶段和用例以[开发与验收流程](开发与验收流程-V1.md)为准。Issue 把其中一小项变成可分派、可验证的工作，PR 记录实现和测试证据。

## 1. 从提需求到关闭 Issue

| 步骤 | 怎么做 | 留下什么 |
|---|---|---|
| 提需求 | 每个可独立验收的功能或缺陷先建 Issue。写明想解决的问题、范围、通过条件、所需样本，引用对应的 REQ、ACC 和阶段编号。阶段 Issue 汇总相关任务。 | 需求、验收清单、依赖及待确认项。 |
| 开发 | 从默认分支开任务分支，分支名带 Issue 编号。开发 agent 先写关键规则的测试或复现步骤，再做实现，跑相关回归。需求变化先更新 Issue 及对应需求文档。 | 与 Issue 对得上的代码、测试和决策。 |
| 提交 PR | PR 写清改动范围、测试命令及结果、平台和人工验收状态。需要提前讨论时可以开草稿 PR。常规 PR 通过自动检查，必要时附可以公开的样卷或复现步骤。 | Issue 编号、测试证据、已验项和待验项。 |
| 回看需求 | 逐条核对 Issue 的验收清单。agent 提供程序、安装包和异常测试结果，用户按需要复核学科内容和纸样。按[开发与验收流程](开发与验收流程-V1.md)分别记录程序、平台和人工验收。 | 对每条通过条件给出结果和证据。 |
| 合并并关闭 | 验收条件齐备后，PR 可用 `Closes #编号`，合并到默认分支时关闭对应 Issue。需要合并后再验的平台、纸样或学科项，用普通引用 `Refs #编号`，等补验通过再关闭。阶段 Issue 等本阶段全部必需验收通过后关闭。 | 可回查的 PR、合并版本和最终验收记录。[GitHub 关联与关闭规则](https://docs.github.com/en/issues/tracking-your-work-with-issues/using-issues/linking-a-pull-request-to-an-issue) |

代码合并、功能验收、安装包发布分别记录。一个 PR 只完成部分需求时，Issue 保持开放并标出剩余工作。GitHub 检查可以验证构建和自动化测试，纸质样卷和学科判断按人工结果记录。默认分支通过 PR 汇入，仓库可配置时把自动检查设为合并前条件。

## 2. Issue 和 PR 的最小模板

**需求 Issue**

- 目标和用户操作
- 对应阶段、REQ 或 ACC 编号
- 本次范围与依赖
- 验收清单，包含正常、失败或重试场景
- 测试样本、平台与人工验收要求

**开发 PR**

- 关联 Issue 和本次改动
- 执行的测试、结果和可公开的证据
- macOS、Windows、学科与纸样的实测或待验状态，适用项分别填写
- 验收已齐备时用关闭引用，仍待验时用普通引用

## 3. 公开仓库和本地资料的边界

| 归属 | 内容 |
|---|---|
| 随代码公开 | 源码、安装与贡献说明、公开版需求和设计、必要的测试说明和测试代码、可公开的测试夹具。自动测试优先用自制小样卷、合成题目和固定 AI 响应，使贡献者不用真实题库、付费账号或个人密钥也能运行。 |
| 经检查后公开 | 有必要的测试文档、演示样卷、打印截图和脱敏日志。使用前检查内容与公开范围，去除个人路径、设备名、账号、题库内容和密钥等与验证无关的信息。 |
| 留在本机 | 真实题库、用户原卷、现有下载的 19 个研究 PDF、私人校审资料、日常导出卷和备份。公开仓库可留必要的来源链接与复现步骤，真实材料验收在本机完成。 |

本地项目已有约 133 MB 研究 PDF。首次同步先列出准备公开的文件，添加忽略规则后检查实际暂存清单、既有提交历史及准备随安装包分发的文件。含本机绝对路径、原卷截图或内部校审细节的研究文档先整理出可公开版本。开源许可证适用于拟公开的项目代码和明确纳入的材料，第三方依赖、字体和样题按各自许可处理。具体代码许可证在首次公开前确认并写入仓库。[GitHub 仓库许可证说明](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/customizing-your-repository/licensing-a-repository)

## 4. AI 密钥和测试

- 真实 API 密钥通过 App 的本机设置录入，保存到系统提供的安全凭据存储。配置样例只写变量名或占位值。真实密钥和本机配置留在设备上。
- 公开仓库的自动化测试使用固定模型响应或本地模拟服务，覆盖正常草稿、超时、异常格式和重复响应。真实模型验收通过单独的本地步骤进行，公开记录只保留必要的测试结论和可公开样本。
- 提交前检查代码、配置、测试夹具、Issue、PR、截图、日志及构建产物，避免密钥进入提交、验收附件、备份或安装包。如发现凭据曾公开，先撤销或轮换，再处理仓库历史和附件，核对新密钥没有进入公开内容。

## 5. 启动时的第一批事项

1. 明确 GitHub 仓库归属、代码许可证和首批公开文件，检查本地目录、提交清单及忽略规则。
2. 确定公开版项目说明、贡献与测试说明、Issue 和 PR 模板。准备一个可公开的最小测试样卷和一份固定模型响应。
3. 建立 M0 阶段 Issue，按可验收结果拆成桌面安装与离线打印、编辑保存与重开、AI 文字和裁图输入等任务。每项按上面的流程走完再关闭。

## 6. 多 Agent 并行协作

多个开发 agent（或多个开发会话）可同时推进不同 Issue。**并行单位是分支，不是工作区**——同一分支同一时刻只允许一个执行者，禁止两个 agent 共享分支或目录。

| 规则 | 要求 |
|---|---|
| 任务认领 | 开工前在 Issue 上自认 assignee 或评论"开工"；未认领的 Issue 不碰 |
| 分支隔离 | 每个任务从 main 拉独立分支 `feat/N-名称`，在独立工作区开发 |
| 接口先行 | 开工先写实施计划，定清 Produces / Consumes（暴露什么、依赖什么）；并行任务只通过接口对齐。如 AI 系列任务共用一个模型网关接口，先做的任务负责定接口 |
| main 单写入口 | main 只经 PR 合并写入；并行分支在 `package.json`、`.gitignore` 等共享文件上的冲突在合并点解决，不在开发中互相等待 |
| 提交即 push | 每个提交立即 push 到本任务分支，避免其他 agent 看不见中间产物而重复劳动 |
| 依赖排序 | 有依赖的任务串行：先做的任务定出共享接口（如模型网关、数据模型）后，依赖它的任务再并行分岔。各阶段启动时按当前看板梳理依赖图 |

实施计划随分支提交并在 [docs/README.md](README.md) 登记；阶段汇总 Issue 跟踪各任务状态。缺 Windows 实测环境等事项按开发与验收流程标"待补验"，不因并行而省略。

当前这份方案用于后续建库和开发交接。建仓库、首次公开推送和发布安装包分别按当次授权执行。
